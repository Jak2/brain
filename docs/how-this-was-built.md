# How this was built

The reasoning behind `brain`, in the order it actually happened. [DECISIONS.md](../DECISIONS.md)
records *what* was decided as 28 numbered entries; this explains *why the shape came out
this way*, what the build found, and what is still unproven.

Written on 2026-09-19, the day the system was built.

---

## 1. The constraint that produced everything

The request was a mentor that teaches you, grows with you, and runs on a **corporate
work laptop**.

That last clause is not a footnote. It kills, in order: any API key, any pip install,
any model download, any cloud service, any database, and any orchestration framework.
Almost every design idea died against it before it was written down.

What survives that environment is very short:

- Python's standard library
- git
- files
- **an AI assistant IT has already approved and installed**

The fourth item is the whole idea. The model is already there — Cursor, Copilot,
whatever the employer blessed. What is missing is not intelligence. It is *direction*.

So this ships no AI. It ships the instructions that drive the one already present.
Nothing to install means nothing to approve, nothing to block, and nothing to explain to
a security team.

## 2. Four questions that decided the architecture

Everything else followed from the answers.

**What can you run at work?** git and Python. No API access. → No framework. No model.

**What must it do there?** Not what was assumed. The first design imagined a local LLM;
the real answer was that Cursor and Copilot were already installed and cleared. The
system became an instruction layer, not an application.

**How does it pick what to teach?** Reactive first — real work is free, real, and
already in front of you — with a skill map as the backstop for what your job never
exposes you to. A fixed curriculum was rejected outright: it dies in week three when
work gets busy, and the abandonment poisons the whole system.

**How do you drive it?** Two commands. `/start` and `/end`. The write-back is the entire
value — an assistant that teaches and records nothing leaves you exactly where you
began — so there is one explicit checkpoint rather than a hope that the model volunteers
a file write mid-conversation.

## 3. The reframe that removed a problem instead of solving it

The first design was *one person's* brain, syncing between a work machine and a home
machine. Most of the early complexity existed to manage that sync.

It was wrong. This is a **distributable system**: anyone clones it, and the data is
always local to their machine. Nothing syncs, so there is nothing to reconcile.

That single correction deleted a whole category of design work. It also forced two
consequences that are now load-bearing:

- **The system repo must be public.** A corporate laptop can't log into a personal
  GitHub, so the only available operation is an anonymous HTTPS clone. Therefore no
  personal data may ever live in this repo — which is why `target.md` is generated by an
  interview instead of shipped.
- **Every clone starts empty.** Cold start is not an edge case, it is the normal first
  run, so it had to be designed as a lesson rather than a setup screen.

When a correction removes work instead of adding it, that is the sign the original
framing was wrong rather than merely incomplete.

## 4. Safety, built as structure rather than as a rule

Notes taken at work can be derived from an employer's code. Those cannot leave the
device. A rule saying "don't push" is worth nothing at 6pm on a Friday.

So it is structural, in three layers:

```
brain/          public system repo — cloned, pulled, never written to
  .gitignore -> data/
  data/         your brain — its own git repo, NO REMOTE CONFIGURED
    local/      employer specifics — gitignored again, inside
```

- The outer repo holds no personal data, so pulling system updates stays clean.
- **The inner repo has no remote**, so `git push` fails with *"no configured push
  destination."* Not discouraged. Impossible.
- Every `/end` splits what it captured: the generalized concept goes to `notes/`,
  employer-free; ticket IDs, internal service names and their code go to `local/`. The
  knowledge is yours and comes with you; the specifics stay put.

A `pre-push` hook was considered and rejected — hooks can be bypassed, aren't installed
by a clone, and depend on being remembered. No remote requires nothing of the user.

The accepted cost: if the machine is reimaged, that brain is gone. That is the correct
trade against the legal exposure, and it is stated plainly rather than mitigated
halfway.

## 5. Where the ideas came from, and what was left behind

**LangChain and LangGraph were rejected** — not for being heavy, but because they are
structurally inert here. Both need *your Python process to call an LLM*. The model lives
inside the assistant and is unreachable from user code, so there would be nothing to
call. Separately, `pip install langchain langgraph` pulls 100+ transitive packages onto
a machine under proxy and security scanning.

What was kept costs nothing: an explicit state object, nodes as pure functions,
conditional edges, and a checkpointer for durable resume. All of it expressible in
markdown and standard-library Python. Because the workflow graph is declared as *data*,
porting to real LangGraph if an API key ever appears is transcription, not redesign.

**Two graphs, not one.**

*The workflow graph* runs a session: `assess → select → teach → verify → capture →
schedule`. Its nodes are the personas. Editing teaching policy means editing a table,
not rewriting a prompt and hoping.

*The knowledge graph* is the point. Notes link with `[[wikilinks]]`, and `brain.py graph`
reports what you cannot see by re-reading your own notes: orphans (a fact you memorized
rather than a concept), hubs (your real foundations, measured), **frontier** (unlearned
skills adjacent to what you already know well — the cheapest next lesson), and bridges
(notes joining two clusters).

Bridges are the closest measurable proxy for the thing that makes senior engineers seem
to absorb new problems faster: their knowledge is *connected*, so a new problem lands
next to five things they already know instead of on empty ground. A system that
optimizes for bridges optimizes for that on purpose.

Links are mandatory from note #1 because metrics can be computed at any time, but links
cannot be retrofitted — nobody goes back and re-reads 200 notes to add them.

**Three loops, each with an exit condition and a checkpoint on disk.** The inner loop
(teach → verify → re-teach differently) exits only when you can explain the thing
unprompted. The day loop exits at a commit. The review loop exits at mastery. State on
disk is what lets any of them be abandoned mid-way and resumed — which is the habit that
makes some engineers look unflappable. It isn't memory; it's that their state was never
in their head.

**Decay exists from day one.** Mastered skills leave rotation; questions expire at 60
days; unlinked notes become archive candidates. The most common death of a second brain
is an unbounded queue turning into a guilt machine. The drain has to exist before the
queue does — retrofitting it means first confronting a backlog of four hundred items,
which is exactly when people quit.

## 6. Personas are contracts, not costumes

A persona with a different *voice* is theater. "Now be skeptical" changes nothing.

A persona with a different **contract** is a function. Each of the six declares what it
Gets, what it must Produce, what it is **Forbidden** from, and when it is Done. The
forbidden column is what makes them real:

- **Teacher** may not ask whether you understood — that invites a polite lie.
- **Examiner** may not see Teacher's reasoning, or the test is rigged.
- **Scribe** may not add anything that wasn't in the exchange.
- **Critic** may not be encouraging, and may not blame effort — three failures is a
  missing prerequisite, not a lack of trying.

**The honest limitation:** today all six run sequentially in one conversation, so that
isolation is *instructed*, not enforced. Telling a model to ignore what it just read is
weaker than it never having read it. Running each persona in its own subagent context
would fix it; nothing here does that yet. It is documented rather than quietly implied
away — see ADR-024.

## 7. One assistant-facing file, many adapters

`AGENTS.md` was formalized in August 2025 and donated to the Linux Foundation's Agentic
AI Foundation in December 2025. **Over 30 agents read it natively** — Codex, Copilot,
Cursor, Gemini CLI, Jules, Aider, Zed, Windsurf, Devin. Writing the protocol once covers
nearly the whole field. Claude Code is the notable exception and reads `CLAUDE.md`,
solved with a one-line `@AGENTS.md` import rather than a second copy.

Adapters are **additive and idempotent**. Bootstrap installs the one for the assistant
that is running and touches no other. Use Cursor in March and Claude in June and both
adapters are there; switch back and nothing needs rebuilding. Adding a future assistant
is a folder, not a code change.

`brain.py` never rewrites itself per assistant. It reads `config.json`; bootstrap writes
`config.json`. Letting each assistant regenerate the engine means the one deterministic
component becomes the least predictable.

## 8. How it was actually built, and what that caught

Nine tasks, test-first, each implemented by a fresh agent with no memory of the others
and then reviewed by an independent one that was told not to trust the implementer's
report. 70 tests. Every review re-ran the reproductions itself.

**Every single Critical defect was in code the plan specified verbatim — not in any
implementer's work.** The plan was the weak link. It contained plausible-looking error
handling that did not survive contact with realistic bad input:

- A single bad byte in a note crashed the daily briefing. `UnicodeDecodeError` is a
  `ValueError`, not an `OSError`, so `except OSError` never caught it.
- A corrupt `state.json` and a typo'd `config.json` crashed it three more ways.
- **A one-word path typo moved the entire brain out of the unpushable repo and into the
  public one.** It took three fix rounds; the last hole was `PureWindowsPath` and
  `PurePosixPath` disagreeing about whether `data\sibling` is one path component or two.
- The no-dependency gate was green for nine tasks **while testing nothing** — the
  filenames in grep's own output satisfied its allow-list.

Each was fixed at the root — one shared guard every caller routes through — rather than
at the call site, because Tasks 6 and 8 would otherwise have reintroduced the same bug.

**The most interesting failure was invisible to every per-task review.** The engine grew
*readers* for `in_flight`, `questions.md`, post-Critic skill files and `graph` output,
while the protocol was never given the matching *writers*. Each half was correct on its
own, so nine reviews passed. Only walking one full cycle end to end exposed it — and it
meant the resume-after-interruption property, the one the whole design was argued to
rest on, could never fire.

The general lesson, worth more than any individual fix: **a verification step that has
never failed is not evidence of anything until you have watched it fail on purpose.**

## 9. What is still unproven

Stated plainly, because a document that only lists strengths is marketing.

1. **Nobody has run a real session yet.** Mechanically the loop closes; whether it
   teaches well is untested.
2. **Whether Cursor or Copilot will follow a protocol this long, faithfully, session
   after session, is unknown.** This is the single biggest risk and it is not a code
   problem. One real session on the target machine will say more than any amount of
   further design.
3. **Persona isolation is instructed, not enforced** (§6).
4. **The verify step can be fooled by a user who wants to be fooled.** Examiner is told
   not to accept "that makes sense," but nothing captures whether you actually produced
   the idea.
5. **Nothing in the system fights disuse.** Decay handles an overflowing queue; no
   feature handles not opening the folder for three weeks. That is the most likely way
   this dies.

## 10. What is deliberately absent

No database. No embeddings. No web UI. No vector search. No bundled model. No cloud
sync. No multi-user support. No dependency of any kind.

Retrieval is deferred until roughly 150 notes, at which point an assistant can no longer
read the relevant subset directly. Until then it is unnecessary, and unnecessary
machinery is what makes a personal tool stop being used.

678 lines of Python for the whole engine. A hand-rolled 20-line frontmatter reader
instead of a YAML dependency. A fixed interval table instead of a spaced-repetition
algorithm. One `articulation_points` function instead of a graph library.

The restraint is the design, not an omission from it.
